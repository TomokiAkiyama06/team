# 検索方式（RAG の検索部分）

## 方針

資料を全文 Claude に渡すことはせず、ページ・スライド・見出し単位のチャンクに分割して SQLite FTS5 に索引し、
質問ごとに関連チャンクだけを検索して渡します。追加サービスなしで日本語資料に実用的な精度を出すことを優先しています。

## 質問が指している資料（全文を渡す）

「今回渡した資料の授業内容を教えて」「第4回の提出物は？」のように**資料そのもの**を尋ねる質問は、質問文の語
（資料・授業・内容など）が資料本文に出てこないため、キーワード検索だけでは見つかりません。そこで回答時
（`Searcher.retrieve()`）は、まず質問が指している資料を特定し、その資料の**全文**を出典付きで渡します。

| 判定 | 内容 |
|---|---|
| ファイル名（`named`） | 質問に資料のファイル名（拡張子なしで 4 文字以上）が含まれる。前後に英数字が続く位置（`lecture10` の中の `lecture1`）や、別の資料のより長いファイル名の一部としての一致は数えない |
| 授業回（`lecture`） | 質問の「第N回」「N回目」などが、ファイル名の授業回と一致する。ファイル名に授業回が無い資料は 1 ページ目の先頭 300 文字から判定（複数の回が並ぶシラバスなどは対象外） |
| スレッド（`thread`） | そのスレッドで `資料登録` / `資料更新` した資料、または以前の質問で指定・参照された資料（`thread_materials` テーブル） |
| 最新（`latest`） | 上記がいずれも無く、「今回渡した資料」「最新のスライド」「今週の課題」のように「今回／最新／今週」の直後（6 文字以内）に資料・授業・課題などの語が続く場合、最も新しく登録された資料。推測なので、回答の冒頭で参照した資料名を伝えるようモデルに指示する |

- 全文は `FOCUS_MATERIAL_MAX_CHARS`（既定 100,000 文字）まで、検索結果とは別枠で渡します。上限を超える資料は、
  先頭チャンク（表紙・概要）と質問に近いチャンクを優先して上限まで選び、資料の順序で並べます（モデルには「一部」と伝えます）。
- そのうえで全資料を対象にキーワード検索を行い、全文を渡していない箇所（シラバスの提出方法など）を追加します。
- 出典IDは指している資料から順に `S1`, `S2`, … と振ります。出典表示は 1 資料 1 行にまとめます（`出典：第4回.pdf p.1 [S1]、p.3 [S3]`）。
- 資料を削除すると、スレッドとの対応も削除されます。

## なぜ「アプリ側の文字 bi-gram ＋ FTS5 unicode61」か

| 候補 | 評価 |
|---|---|
| FTS5 `unicode61` をそのまま使う | 日本語は空白で区切られないため、文全体が 1 トークンになり部分一致できない |
| FTS5 `trigram` トークナイザ | 3 文字未満の語で検索できない。「課題」「締切」「提出」など授業で重要な語の多くが 2 文字 |
| MeCab / Sudachi 等の形態素解析 | 辞書の導入・管理が必要で、授業固有の専門用語や表記ゆれで取りこぼす。Docker イメージも肥大化 |
| ベクトル検索（埋め込み） | 埋め込み API（外部依存・費用・資料の追加送信）またはローカルモデル（メモリ・CPU）が必要。固有名詞・授業回番号の完全一致に弱い |
| **文字 bi-gram（採用）** | 辞書不要で 2 文字語を検索でき、未知語・専門用語にも強い。SQLite 標準機能のみで動作 |

実装：アプリ側（`textnorm.py`）で正規化した文字 bi-gram を空白区切りで生成し、FTS5 の `unicode61` トークナイザには
「空白区切りの単語列」として格納します。英数字の連続は単語としても追加します（`python`, `html` などの完全一致用）。

## 正規化ルール（索引と検索で共通）

1. Unicode NFKC 正規化（全角英数→半角、半角カナ→全角など）と小文字化
2. 授業回の漢数字を算用数字に統一（`第三回` → `第3回`、`第十二回` → `第12回`）
3. 数字の先頭ゼロを除去（`第03回` → `第3回`、`lecture01` → `lecture1`）
4. 空白・句読点・括弧・記号で区切り、各区間を文字 bi-gram 化（1 文字の区間はそのまま）
5. 検索時はひらがなだけの bi-gram（「について」の「つい」「いて」など助詞・語尾）と、質問によく出るが資料の特定に
   役立たない一般語（資料・授業・内容・今回・教え・説明・要約など。`textnorm.GENERIC_QUERY_BIGRAMS`）を除外。
   ただし他に手掛かりが無い場合は残す（索引には影響しないため再インデックスは不要）

## ランキング

1. **BM25**：FTS5 の `bm25()` で、タイトル列（ファイル名＋見出し）を本文列より重く評価します。ファイル名に「第3回」「課題提出方法」などが含まれる資料が上位に来ます。
2. **授業回番号の一致**：質問に「第3回」「3回目」「lecture 3」などがあれば、ファイル名・見出しの授業回番号が一致する資料を加点します。
3. **資料ごとの上限**：同じ資料から採用するチャンク数を `SEARCH_MAX_PER_MATERIAL` に制限し、1 資料が結果を占有しないようにします。
4. **重複除去**：索引時に同一資料内の完全重複チャンク（毎ページ同じヘッダー・フッターなど）を除外し、検索時は bi-gram 集合の類似度が高いチャンクを間引きます。
5. **件数・文字数の上限**：上位 `SEARCH_TOP_K` 件、合計 `SEARCH_CONTEXT_MAX_CHARS` 文字までをモデルに渡します。
6. **追加質問**：スレッド内の追加質問（「それの締切は？」など）は手掛かりが少ないため、直前のユーザー質問も補助的に検索語へ加えます。

## 検索結果の十分性

各チャンクが質問のトークンをどれだけ含むか（被覆率）を計算し、15% 未満のチャンクは採用しません（`search.MIN_COVERAGE`）。
上位結果の被覆率から `sufficient` / `weak` / `none` を判定し、モデルに伝えます（質問が指している資料を渡した場合は `sufficient`）。
`weak` / `none` の場合、モデルは資料に該当が無いことを短く示したうえで、AI の一般知識で回答します（「補足（AIの一般知識）」として区別）。

## 出典 ID

各チャンクに `S1`, `S2`, … の出典 ID を付けて渡し、回答中で使用した ID を出力させます。回答後、ID を実際の検索結果と照合し、
実在しない ID は除去します。出典表示（`出典：第3回講義資料.pdf p.12`）は DB のメタデータからコードで生成します。

## 長大な資料とメモリ

抽出・チャンク化は子プロセスでストリーム処理し、チャンクを JSONL に書き出してからバッチで DB に挿入するため、資料サイズに比例してボット本体のメモリが増えることはありません。

## 将来の拡張：ベクトル検索

検索品質が不足する場合は、現在の全文検索を残したまま埋め込みベクトルによる検索を追加し、両者のスコアを統合する
ハイブリッド検索を想定しています（例：ローカル埋め込みモデル＋ `sqlite-vec`）。その場合も、外部への資料送信の有無・費用・
メモリ使用量を考慮して選定し、本ドキュメントを更新してください。
